# Вход Windows и первый администратор

Приложение использует Windows Negotiate. Пользователь определяется по SID существующей учётной записи Windows. Приложение не создаёт Windows-аккаунты и не меняет их пароли. Учётные записи, роли `User`/`Admin` и глобальные настройки хранятся через EF Core в независимой SQLite БД (`ServiceDbContext`). Данные печати остаются в SQL Server с отдельным `ApplicationDbContext`.

Служебная SQLite использует собственные миграции из `DiplomaTry2/Data/ServiceMigrations`, применяемые при запуске под общей межпроцессной блокировкой. Для добавления миграций указывайте `--context ServiceDbContext`; для SQL Server — `--context ApplicationDbContext`. Фабрика проектирования служебного контекста использует базу в памяти, чтобы генерация миграций не запускала приложение и не обращалась к рабочим базам.

При первом запуске новой версии прежняя SQLite XPO автоматически переводится на EF Core. Перед обновлением остановите все экземпляры старой версии. Рядом с файлом базы создаётся резервная копия `<путь-к-базе>.xpo-backup`. Активные учётные записи, роли, настройки, список серверов и зашифрованные значения сохраняются; записи, помеченные XPO как удалённые, не восстанавливаются. Замена таблиц и запись истории миграции выполняются в одной транзакции. При ошибке исходная схема остаётся, резервная копия сохраняется; перед повторной попыткой проверьте причину ошибки и переместите копию, поскольку существующая копия не перезаписывается. Сохраните также каталог ключей Data Protection: он нужен для расшифровки подключения.

## Постоянное хранилище

`ServiceDatabase:Path` по умолчанию равен `%ProgramData%/DiplomaTry2/service.sqlite`. Каталог должен находиться вне каталога приложения и `wwwroot`; при обновлении приложения он сохраняется. Предоставьте учётной записи службы/пула IIS право изменения этого каталога, а обычным пользователям не предоставляйте доступ к SQLite и каталогу `keys`.

Строка подключения зашифрована ASP.NET Data Protection. Ключи сохраняются рядом с SQLite в `keys` и защищены Windows DPAPI от имени процесса. Сохраняйте резервную копию SQLite **вместе с ключами**; сохраняйте Windows-учётную запись запуска службы. Перенос ключей на другой сервер/под другую учётную запись требует отдельного планирования DPAPI и повторного ввода подключения.

`ConnectionStrings:DefaultConnection` нужен для первичного переноса из прежней БД и начального заполнения настроек. После создания SQLite рабочее подключение берётся из неё. Изменение appsettings не перезаписывает сохранённые настройки. Исходное подключение для переноса также сохраняется защищённо и не меняется при выборе другой основной БД.

## Перенос и первоначальный администратор

При первом обычном запуске фоновая служба читает прежние `AspNetUsers`, `AspNetRoles`, `AspNetUserRoles`. SID сохраняются; старые строковые идентификаторы разрешаются через имя Windows-аккаунта. Назначения объединяются по SID с приоритетом Admin. Учётные записи, назначения и отметка завершения фиксируются одной транзакцией SQLite. Исходная SQL Server БД не изменяется. Повторные запуски не дублируют пользователей и не возвращают отозванные роли.

Если старая БД недоступна или Windows-имя не разрешается, перенос повторяется через 30 секунд. Существующая SQLite-авторизация продолжает работать. До завершения переноса открытое назначение первого администратора блокируется. Если доступ к старой БД восстановить пока невозможно, оператор сервера может явно задать `ServiceDatabase:BootstrapAdminSid` (SID доверенного Windows-пользователя, например из `whoami /user`). Только этот пользователь может локально выполнить `/Setup/claim`, только при отсутствии администратора. После настройки удалите значение BootstrapAdminSid из конфигурации.

Для чистой установки оставьте `DefaultConnection` пустым: перенос считается завершённым, и первый Windows-администратор назначается локально через `/Setup`. SQL Server для этого не требуется. Не подменяйте пустым подключением исходную конфигурацию существующей установки до первого запуска переноса.

## Запуск напрямую через Kestrel

После сборки и настройки постоянного каталога SQLite:

```powershell
dotnet run --project DiplomaTry2/DiplomaTry2.csproj --launch-profile https
```

Откройте адрес с того же компьютера под той Windows-учётной записью, которую нужно назначить первым администратором. На главной странице перейдите в «Первоначальная настройка» и нажмите «Назначить меня администратором». Страница доступна по `/Setup`. Удалённый браузер не может выполнить первичное назначение.

Если браузер запрашивает учётные данные, используйте текущую учётную запись Windows. Для бесшовного входа адрес приложения должен входить в зону локальной интрасети/доверенных сайтов с разрешённым автоматическим входом по политике браузера.

## IIS и IIS Express

Для IIS Express в `Properties/launchSettings.json` включена Windows-аутентификация и отключена анонимная. Для настоящего IIS установите компонент **Windows Authentication**, включите его для сайта и отключите **Anonymous Authentication**. Первое назначение откройте локально на сервере. Настройка профиля IIS Express не меняет настройки опубликованного сайта IIS.

Windows-аутентификация веб-пользователя определяет права в интерфейсе. SQL Server и сервер печати по умолчанию вызываются от имени процесса приложения или его пула IIS; их доступ настраивается отдельно. Проксирование Negotiate требует особой настройки и здесь не проверялось.

## Проверка

После назначения перезагрузите страницу. Администратор увидит выбор источника и страницы «Загрузить принтеры» и «История печати». Другой Windows-пользователь получит отказ 403 на страницах импорта. Повторная попытка первичного назначения не создаст второго администратора.

На `/settings` Admin меняет подключение к SQL Server, проверяет его, задаёт глобальный сервер печати и управляет ролями существующих Windows-пользователей. User просматривает разрешённые параметры. Изменения повторно проверяют текущую роль в SQLite на сервере, включая уже открытые Blazor-сеансы. Последнего Admin удалить или понизить нельзя, в том числе конкурентными запросами.

Подключение из формы всегда использует шифрование. Переключатель «Доверять сертификату сервера» по умолчанию выключен: сертификат SQL Server проверяется. Для локальной установки с самоподписанным сертификатом Admin может включить его; тогда проверка сертификата отключается, шифрование остаётся включённым. Выбор применяется при проверке и сохранении подключения и восстанавливается при повторном открытии формы. Пароль не выводится; пустое поле сохраняет прежний пароль только для прежнего сервера, БД и SQL-логина. При сохранении выполняется проверка таблиц, типов/размеров столбцов и уникальных индексов импорта; несовместимое или недоступное подключение не заменяет рабочее. Схема SQL Server при сохранении не создаётся и не изменяется. Подготовьте выбранную БД отдельно существующей цепочкой миграций; `--migrate` остаётся отдельной явной командой для текущего подключения. Если SQLite ещё не создана, эта команда использует начальное подключение из конфигурации.

Новые операции используют актуальные глобальные настройки без перезапуска. Импорт закрепляет одну пару подключения и источника на все пакеты; уже начатый импорт заканчивается в прежней БД. Одинаковые имена очередей разных источников получают разные внутренние ключи целевого принтера. Исторические записи не переписываются.

В разделе «База данных» сохраняется список подключений в служебной SQLite. Текущее подключение автоматически добавляется при обновлении. Admin нажимает «Добавить подключение», заполняет параметры и сохраняет их в список; добавление не меняет активную БД. Для переключения нажмите «Сделать активной» в строке нужной БД. При сохранении, проверке и переключении проверяются доступность SQL Server и совместимость схемы; ошибка оставляет активное подключение прежним. Создание баз и изменение их схемы из списка не выполняются.

Для каждого подключения сохраняются сервер, база, режим входа, SQL-логин и выбор доверия сертификату; полная строка с паролем зашифрована Data Protection. При изменении записи пустой пароль сохраняет пароль именно этой записи, только если сервер, база и SQL-логин остаются прежними. «Изменить» обновляет выбранную запись, а изменение активной записи сразу применяется к новым операциям. Дубликаты одной пары сервер/БД с тем же режимом входа и логином не добавляются. Удаление из списка не удаляет саму базу SQL Server; активную запись нельзя удалить до переключения. User может просматривать список, управлять и проверять подключения может только Admin.

Реальный сервер печати задаётся глобально. Старые имена из sessionStorage игнорируются. В `/test-tools` Admin может выбирать Fixture и сценарии для своей вкладки; User не получает доступ к тестовому источнику. Настройки отображения таблиц остаются в браузере.

В разделе «Сервер печати» сохраняется постоянный список имён/IP в SQLite. При обновлении прежний активный сервер автоматически добавляется в список. Добавление сервера не меняет активный источник; нажмите «Сделать активным» в строке нужного сохранённого сервера. Переключение общее для приложения, уже начатые операции используют прежний источник. Повторное добавление одного имени в разном регистре не создаёт дубли. Активный сервер нельзя удалить до переключения на другой. User видит список и текущий сервер, а изменения и сетевые проверки доступны Admin.

«Проверить» выполняет с сервера приложения одно разрешение DNS, один ICMP echo с 32 байтами и одно TCP-подключение к порту RPC 135, без перечисления принтеров и чтения журналов. DNS ограничен двумя секундами, ping и TCP запускаются параллельно с тем же ограничением; одновременно допускаются до четырёх проверок. Результат не переключает сервер и не сохраняет адрес автоматически. Проверка показывает выбранный IP; отсутствие ответа ICMP может означать блокировку firewall. Ответ ping/доступность TCP 135 не подтверждают работу Spooler, доступность динамических RPC-портов или права учётной записи службы.

При незаданном/недоступном SQL Server Windows-вход и `/settings` работают; страницы данных показывают ошибку получения данных. Служебная SQLite должна оставаться доступной.

Автоматические проверки: `dotnet test DiplomaTry2.ImportTests/DiplomaTry2.ImportTests.csproj` с `DIPLOMA_TEST_CONNECTION`, указывающим на выделенную мигрированную тестовую SQL Server БД. Браузерный сценарий: `node scripts/test-settings.cjs [путь-к-playwright] [URL] [каталог-скриншотов]`. Запускайте браузерный сценарий только с отдельной временной SQLite и единственным тестовым Admin: он проверяет сохранение, две вкладки, старое sessionStorage, сценарии Fixture, защиту последнего Admin и отказ нерабочего SQL-подключения.
