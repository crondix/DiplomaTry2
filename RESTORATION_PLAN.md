# План постепенного восстановления DiplomaTry2

Дата: 25.09.2026. Статус: этапы 1–5 выполнены для отдельной тестовой БД; этап 6 в работе.

## Цель первого рабочего варианта

Приложение запускается, подключается к SQL Server, получает принтеры и события из тестового источника, сохраняет их и показывает в интерфейсе. Повторная загрузка не создаёт дубликаты, ошибки видны пользователю. Затем тестовый источник можно заменить реальным сервером печати.

SQL Server и сервер печати доступны вне песочницы Codex. Для тестовых записей используется отдельная база `Diploma_Restoration_Test`.

## Что установлено при осмотре

- Основной путь запуска — `DiplomaTry2/DiplomaTry2.csproj` и корневой `DiplomaTry2.sln`. Проекты уже переведены на .NET 10; на машине установлен SDK 10.0.401.
- Обычная параллельная сборка, в том числе вне песочницы Codex, иногда завершается ошибками MSB4216/MSB4027 в `ComputeWasmBuildAssets` клиентского проекта: внешний сервер задач MSBuild не подключается. Отключение повторного использования узлов MSBuild устраняет сбой вне песочницы; последовательная контрольная пересборка прошла успешно (118 предупреждений, 0 ошибок). В песочнице сбой сохраняется и с `-m:1 -nodeReuse:false`.
- В рабочем дереве есть незакоммиченные изменения проектов, миграций, KMeans и CSS. Их нужно учитывать при формировании исходной точки восстановления.
- В `Program.cs` миграции автоматически применяются при доступной БД. Если соединение невозможно, инициализация схемы пропускается.
- У одного `ApplicationDbContext` есть несколько миграций создания схемы в двух каталогах. Они повторно создают часть таблиц; требуется сверка с фактической схемой и историей миграций.
- Страницы зависят от конкретного `PrintServerService`, обработка событий — от конкретного `EventLogService`. Существующий `IPrintServerService` не служит общей точкой подключения этих компонентов и содержит Windows-тип `PrintQueue`.
- Имя `vm-print` задано значением по умолчанию в `EventLogService`; изменение настройки сервера не покрывает этот путь чтения событий.
- Импорт событий загружает всю таблицу, берёт `LastOrDefault()` без сортировки и отбирает новые записи только по времени. Идентификатор записи исходного журнала в модель события не переносится.
- Страница событий может установить признак успеха после ошибки сервиса; при каждом обновлении добавляет подписки на события.
- Автоматических тестовых проектов не обнаружено. Кластеризация пока не подключена к рабочему сценарию веб-приложения.

Ошибка возвращается вместе со счётчиками уже завершённых порций и показывается в интерфейсе как ошибка.

Новая миграция `20260925010000_PrintEventImport` применена только к `Diploma_Restoration_Test`. Старые записи не содержали номера журнала, поэтому миграция оставляет их с пустой идентичностью: достоверно сопоставить их с исходными событиями задним числом нельзя. Первая загрузка после обновления может добавить события, уже присутствовавшие среди старых строк; последующие загрузки их не дублируют. На момент проверки в тестовой базе было 4870 старых событий. Полный импорт реального журнала не запускался.

Добавлен проект `DiplomaTry2.ImportTests` в корневое решение. Четыре интеграционных теста на отдельной SQL Server БД проверили повторную загрузку, одинаковое время и изменённый порядок, неизвестный принтер, сбой после первой порции и возобновление, конкурентный запуск и повторное использование номера после очистки журнала. Все прошли; тестовые строки удалены. Команда проверки:

```powershell
$env:DIPLOMA_TEST_CONNECTION = (Get-Content DiplomaTry2/appsettings.Development.json -Raw | ConvertFrom-Json).ConnectionStrings.DefaultConnection
dotnet test DiplomaTry2.sln --no-restore --nologo -m:1 -nodeReuse:false -clp:ErrorsOnly
```

После скриншота необработанного исключения отдельно проверен запуск без строки подключения. Теперь приложение пишет причину в консоль и завершает работу с кодом 1; при `ASPNETCORE_ENVIRONMENT=Development` с уже обновлённой тестовой БД приложение запускается. Это не заменяет проверку реального сервера на этапе 7.

**Промежуточный результат 25.09.2026.** Переписана страница событий: отдельные состояния чтения, импорта, результата и ошибки; повторный запуск блокируется; подписка на прогресс снимается после операции и при уничтожении компонента. Меню ведёт к рабочим сценариям, шаблонная главная страница заменена.

По уточнению пользователя парольная Identity-аутентификация заменена Windows Negotiate. Приложение привязывает роль `Admin` к SID пользователя Windows в существующих таблицах Identity. На главной странице до появления первого Windows-администратора есть переход на `/Setup`. Назначить себя администратором можно только из локального браузера на машине приложения, после Windows-аутентификации и подтверждения формы с защитой от CSRF. Операция сериализуется в SQL Server; второй первый администратор не создаётся. Страницы импорта принтеров и событий требуют роль `Admin`; чтение принтеров источника и сохранённых моделей требует Windows-входа. Старые `/Account/*` маршруты закрыты; пароль и email больше не участвуют во входе. Для IIS Express включена Windows-аутентификация; для настоящего IIS её нужно включить в настройках сайта и отключить анонимный доступ.

Роль пока не назначалась по выбору пользователя. Для автоматической проверки добавлен `scripts/check-restoration.ps1`: восстановление пакетов, сборка и интеграционные тесты при заданной `DIPLOMA_TEST_CONNECTION`.

Проверочный список: запустить приложение и открыть его локально под нужной Windows-учётной записью; на `/Setup` нажать «Назначить меня администратором»; открыть `/netPrinters` и дважды загрузить тестовые принтеры (второй импорт без новых дублей); открыть `/Events` и дважды импортировать события (второй импорт без новых строк); перезагрузить страницы и убедиться, что данные сохранены; открыть приложение под другой Windows-учётной записью и проверить отказ на страницах импорта; проверить повторное открытие `/Setup` без возможности назначить нового первого администратора. Для запуска автоматической проверки задать `DIPLOMA_TEST_CONNECTION` на отдельную тестовую БД и выполнить `./scripts/check-restoration.ps1`.
