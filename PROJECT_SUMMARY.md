# Краткая карта проекта DiplomaTry2

Актуально по состоянию репозитория на 25.09.2026. Это дипломный прототип веб-системы для инвентаризации сетевых принтеров и учёта успешных заданий печати. Основной источник данных — Windows print server; события печати берутся из его журнала, а справочники и история хранятся в SQL Server.

## Что здесь главное

| --- | --- | --- |
| [`DiplomaTry2/`](DiplomaTry2/) | Основное ASP.NET Core / Blazor-приложение, серверные компоненты, сервисы, EF Core, Identity | Главный проект для запуска |
| [`DiplomaTry2.Client/`](DiplomaTry2.Client/) | Клиентские Blazor WebAssembly-компоненты и состояние аутентификации | Подключён к основному проекту; большая часть рабочих страниц находится на сервере |
| [`DiplomaModels/`](DiplomaModels/) | Сущности принтеров, моделей, пользователей печати, файлов и событий | Общие модели для сервера и клиента |

Корневое решение — [`DiplomaTry2.sln`](DiplomaTry2.sln). Папка `DiplomaWPF` присутствует, но исходников проекта в ней не обнаружено.

## Основные сценарии

1. **Список принтеров.** [`PrintServerService`](DiplomaTry2/Services/PrintServerService.cs) через Windows `System.Printing` читает очереди с принт-сервера и извлекает имя, сетевой порт/IP, драйвер (модель), комментарий и состояние. Страница `/NetworkPrintersList` показывает результат напрямую, без записи в БД.
2. **Наполнение справочников.** На `/netPrinters` кнопка загружает модели и очереди выбранного источника в БД через [`NetPrintersService`](DiplomaTry2/Services/NetPrintersService.cs) и показывает сохранённые принтеры. `/PrinterNameVerification` показывает сохранённые модели. Повторная загрузка обновляет очереди по ключу источника и имени, не создавая дублей.
3. **История печати.** [`EventLogService`](DiplomaTry2/Services/EventLogService.cs) читает удалённый журнал `Microsoft-Windows-PrintService/Operational`, событие **307**. [`EventLogProcessingService`](DiplomaTry2/Services/EventLogProcessingService.cs) преобразует записи в сущности, сопоставляет отправителя, компьютер, принтер и документ с БД и сохраняет новые события. На `/Events` можно запустить актуализацию и посмотреть последние 50 записей.
4. **Учётные записи.** [`Program.cs`](DiplomaTry2/Program.cs) использует Windows Negotiate для входа. Роль Admin привязана к SID учётной записи Windows в таблицах Identity. Первый администратор назначает себя через локальную страницу `/Setup`; старые страницы входа с паролем в `Components/Account` недоступны.

Часть меню и страниц (`Home`, `Counter`, `Weather`, `/js`, `/TestS`) — шаблонные или экспериментальные экраны, а не основной сценарий.

## Данные и зависимости

Контекст [`ApplicationDbContext`](DiplomaTry2/Data/ApplicationDbContext.cs) содержит таблицы `NetworkPrinters`, `PrinterModels`, `PaperSizes`, `EventsSuccessfulPrinting`, `PrintserverEvents`, `SenderDevices`, `SentPrintingFiles`, `Senders`, `TargetPrinters`, `DocumentNames`, `ChangeLogs` и таблицы Identity. Схема задаётся миграциями EF Core в `DiplomaTry2/Migrations` и `DiplomaTry2/Data/Migrations`.

Служебное хранилище также использует EF Core: отдельный [`ServiceDbContext`](DiplomaTry2/Data/ServiceDbContext.cs) работает с локальной SQLite вне каталога приложения. В нём находятся Windows-аккаунты, роли, глобальные настройки и серверы печати. Его миграции лежат в `DiplomaTry2/Data/ServiceMigrations` и применяются автоматически под межпроцессной блокировкой. Прежняя схема XPO переносится транзакционно с резервной копией `.xpo-backup`; подробности обновления приведены в [`WINDOWS_AUTH_SETUP.md`](WINDOWS_AUTH_SETUP.md). SQL Server и SQLite используют отдельные контексты и цепочки миграций.

Основное приложение ориентировано на **Windows и .NET 10** (`net10.0-windows`, WPF/System.Printing), **SQL Server** и доступ к удалённому принт-серверу/его журналу. В [`appsettings.Development.json`](DiplomaTry2/appsettings.Development.json) указана отдельная тестовая БД `Diploma_Restoration_Test` на `PC-UOIT141\SQLEXPRESS`; в других средах подключение передаётся через `ConnectionStrings__DefaultConnection`. Источник печати по умолчанию тестовый; реальный `vm-print` выбирается через `PrintSource__Mode=Windows`. Вне песочницы Codex подтверждено чтение очередей и журнала сервера. Профиль HTTPS использует `https://localhost:7197`.

Для локального запуска после настройки окружения: `dotnet run --project DiplomaTry2/DiplomaTry2.csproj --launch-profile https`. Обычный старт проверяет подключение, наличие ожидающих миграций и чтение счётчиков данных; схему он не меняет. Миграции применяются отдельной командой `dotnet run --project DiplomaTry2/DiplomaTry2.csproj --no-launch-profile -- --migrate` с заданным подключением. Страницы принтеров и моделей и тестовый импорт событий проверены в браузере; полный импорт реального журнала остаётся на последующих этапах.

Источник можно сменить прямо в верхней панели приложения. Выбор сохраняется в пределах вкладки браузера; для тестового режима доступны обычный, пустой и ошибочный наборы. Смена источника влияет на последующие запросы, но не разделяет уже сохранённые данные БД.

## Кластеризация


[`KMeans<T>`](Infrastructure/KMeans.cs) и [`ClusterAnalysisUseCase<T,B>`](Diploma.Application/UseCase/ClusterAnalysisUseCase.cs) выглядят как задел для анализа данных печати: выбор признаков → матрица → нормализация → распределение по кластерам. В `Program.cs` веб-приложения нет регистрации этих классов, вызовов из страниц тоже нет. В use case нормализованная матрица вычисляется, но не передаётся анализатору. Поэтому кластеризацию следует считать незавершённой отдельной веткой функциональности.

## Текущее состояние и что проверить при продолжении

- Последний коммит в истории — **19.04.2025**, изменения KMeans. Автоматических тестовых проектов в репозитории не обнаружено.
- Проекты корневого решения обновлены до **.NET 10**, пакеты ASP.NET Core / EF Core — до **10.0.12**. На Windows с SDK **10.0.401** команды `dotnet restore DiplomaTry2.sln --nologo` и `dotnet build DiplomaTry2.sln --no-restore --nologo -m:1 -nodeReuse:false` проходят вне песочницы Codex. Полная пересборка дала **118 предупреждений, 0 ошибок**; рабочие сценарии остаются непроверенными. Обычная параллельная сборка без флагов может завершаться MSB4216/MSB4027 при подключении вспомогательного процесса MSBuild для WebAssembly, в песочнице сбой сохраняется и с флагами. Диагностика и приоритет предупреждений записаны в `RESTORATION_PLAN.md`.
- Для сборки исправлены старые конфликты: классу миграции 2025 года дано уникальное имя без изменения её ID; `KMeans<T>` реализует две перегрузки интерфейса. Во втором этапе миграция 2025 года исправлена: она меняет только nullability двух полей, не создавая повторно все таблицы. Цепочка проверена на новой тестовой БД и при обновлении с состояния 2024 года. Существующих рабочих данных на доступном экземпляре SQL Server не обнаружено; их схему и историю при появлении нужно сверить отдельно.
- Отдельный `Diploma Backend` переведён на .NET 10, однако всё ещё **не собирается**: в скопированных сервисах отсутствуют ссылки на `DiplomaModels`, основной контекст БД и Windows API печати. В основном решении этого проекта нет.
- Импорт событий на этапе 5 переведён на порции по `RecordId`, контрольную точку источника и уникальный индекс в БД. Четыре интеграционных теста проходят на отдельной тестовой БД. Старые события без идентификатора журнала нельзя достоверно сопоставить с источником; первый повторный импорт может создать копии старых строк.
- В рабочем дереве до создания этой памятки уже были изменены несколько CSS-файлов и `wwwroot/bootstrap/bootstrap.min.css`, а также лежал неотслеживаемый `DiplomaModels/DiplomaModels.sln`. Эта памятка их не меняет.
